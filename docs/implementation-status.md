# Implementation and validation status

The core is now an installable `epsm_core` 2.0.1 package. The old package, custom unit
framework, alternate engine, archetype registry and Honeybee translation path have
been removed. Source and dirty-worktree backups were saved before cleanup at
`/private/tmp/epsm-reset-backup.83OZAh`, including a source tarball, binary diff and
Git history bundle. Existing archives, weather and v1 datasets were not removed.

Implemented locally:

- Frozen, validated building specs and explicit assumption/provenance assembly.
- Direct EnergyPlus 24.2 epJSON with Kiva, roofs, airflow, schedules and shading.
- Whole-building/per-storey zones, concave and courtyard polygons, multipolygons,
  full basements, immutable renovation operations and district orchestration.
- Validated SQL/hourly results, FVP delivery accounting and optional PVWatts V8.
- CLI schema/validation/compile/run/IDF export, packaging and CI unit test workflow.
- Sibling `epsm_workflows` package with ingestion, sampling, storage, OAT, QA and ML.
- Optional `epsm_data.epsm_core_adapter` using complete physical layer properties.

Validation before the campaign: 27 combined tests passed, including seven real annual
EnergyPlus geometry/roof/foundation cases and campaign/store tests. A 10 kW PVWatts
V8 smoke test with Gothenburg weather produced 9,277.53 kWh; hourly and annual output
agreed. IDF conversion through EnergyPlus passed. The design generator produced
10,000 rows and passed allocation, LHS strata and matched-pair area/volume checks.

The authoritative simulation status is in
`results/epsm_core_2_0_1_10000/store.duckdb`. Creating the design does not mean those
simulations have completed. OAT and pilot reports are generated by the campaign
runner; the full dataset and ML report must be checked against that catalogue.

The earlier `results/epsm_core_v2_10000` directory is an interrupted validation
campaign used to identify a thread-based SQL parsing bottleneck. Its outputs are
kept separately. Production campaign workers use separate processes, with one
catalogue writer, and retain SQL as verified gzip files after Parquet validation.

The 2.0.0 campaign was stopped after warning review exposed incomplete internal-mass
view factors. Two replays changed annual heating by 11.5–11.7% simply by splitting
the aggregated surface. Those outputs are diagnostic data, not approved training
rows. Release 2.0.0 is marked withdrawn/prerelease. Compiler 2.0.1 uses individual
half-slab faces per storey, preserves physical heat capacity, and rejects incomplete
view-factor warnings. Its run IDs and campaign manifest differ; no old targets are
reused. A regression fixture and layer/heat-capacity conservation test cover this fix.

See architecture.md for the documented approximations: simplified zoning, equivalent
thermal bridges, split Kiva foundations for courtyard tessellation, sealed cold
attics, operating airflow, sensible-only FVP extraction and daily repeated schedules.
